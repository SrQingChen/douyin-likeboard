# 抖音直播间点赞限额（3000/时）机制调研

> 性质声明：抖音**没有公开文档**描述该限额。以下综合了（a）项目需求方的一手观察、（b）社区通行认知整理。属"观察性结论"，非官方规范。本环境外网搜索受限（Bing/Baidu/DDG 均不可达），未能补充更多二手来源，已如实标注。

## 1. 观察到的行为（需求方一手观察）

1. **窗口起点**：从**本场第一次点赞**开始计时，1 小时窗口；
2. **名义上限**：约 3000 赞/窗口；但实际触发点有随机浮动——观察到 2999、2998，甚至 2880 等更低值直接触发；
3. **触发表现**：客户端提示「点赞太快了，休息一下」（休息一下），此后继续点击**不再增加**点赞计数（服务端不计数）；
4. 窗口过后恢复可赞。

## 2. 机制推断（与观察一致的模型）

- 服务端按 用户×房间（或用户全局）维护**滚动 1h 计数器**；到达阈值后进入软封锁（该窗口内丢弃后续点赞）；
- 阈值不是精确 3000，更像 **~2800–3000 的模糊区间**（可能含风控画像动态下调：新设备/新账号/行为异常者阈值更低）；
- 推论：单人**有效**点赞速率上限 ≈ 50/分钟均值；连点器的高频点击在触顶后被服务端丢弃，**不会体现在房间 total 里**。

## 3. 对本项目（旁观计数器）的影响

1. **口径**：本工具统计的是"**有效赞**"（服务端实际计入的），与直播间页面展示的"本场点赞"一致——这正 是排行榜想要的口径；被限额吞掉的点击本来就无意义，不丢数据。
2. **连点器场景**：连点器在限额内的点击全部被 count 字段如实携带（参考项目实测 count=10/条、Σcount==Δtotal），统计不会漏；
3. **触顶特征（可观测推断）**：某用户高速点赞后计数在 ~2800–3000 区间**突然停滞**、且房间 total 增速来自他人 → 可推断其触顶。榜单可给该用户显示「⚖️ 限额中」小标记（推断性标注，非确定事实）；
4. **速度纪录的上界**：单人 60s 峰值速度理论上限 ~3000/窗口 折算（短窗爆发可达每分钟数百），用于"手速之王"数值的合理性校验。

## 4. 待实测补充（用户使用中可验证）

- 窗口是"首次点赞起 1h 固定"还是"滚动 1h"（观察支持前者）；
- 阈值浮动的分布（是否与账号画像相关）；
- 触顶提示是否仅发送端可见（旁观端无信号，本工具只能靠停滞推断）。

> 以上 4 点不影响本项目开发——计数口径不依赖限额机制的精确参数。
