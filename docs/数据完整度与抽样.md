# 数据完整度与抖音点赞广播抽样机制（实测）

> 2026-11-07 实测发现，调研阶段未覆盖。本文记录实验数据、结论与工程对策。

## 现象

LikeMessage 的 `count`（本条点赞数）逐条累加后，与 `total`（房间累计）差值不等：
**服务端只把一部分点赞以 LikeMessage 形式广播给单个客户端**（抽样下发）。
`coverage = Σcount / Δtotal` 如实反映该比例（控制台与榜单均有展示，缺口不虚补）。

## 实验数据（同一活跃房间，2026-11-07）

| 采集方式 | coverage（稳定值） |
|---|---|
| 匿名 profile × 1 路 | ~31% |
| 匿名 profile × 2 标签 | ~44.6% |
| 匿名 profile × 4 标签 | ~46.2% |
| **登录态 profile × 1 路**（参考项目 dy-sniffer/frames6 夹具） | **~79.9%** |

## 结论

1. 抽样按连接独立、但**同 profile 多标签的独立性有限**（4 路仅 +15pp）；
2. **登录态是完整度的最大杠杆**（79.9% vs 31%）——服务端对登录用户下发更完整的广播流；
3. 多标签采集仍有正收益，默认 2 路（CAPTURE_TABS 可调 1-4），成本可忽略；
4. 排行榜语义下的偏差特征：**高频用户（连点器/头部）抽样比例稳定**（按活跃度等比），**相对排序与冠亚季军判定不受影响**，绝对数值按 coverage 比例偏低；长尾轻用户偶有漏计。

## 使用建议（写入 README 与设置页）

- 追求最高完整度：在捕获 Chrome 窗口内**登录你的抖音小号**（一次登录长期有效，cookie 存本地 profile）；
- 完整度实时展示在控制台概览卡与榜单角标（低于 99% 时出现 ⚠ 标注）；
- 换更活跃的时段/房间，抽样率也会有波动（服务器负载相关）。
