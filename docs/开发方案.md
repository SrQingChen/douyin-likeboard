## 0. 一句话概述

**纯被动旁听**抖音直播间 WebSocket 推送流，实时解码 `WebcastLikeMessage`，按 `secUid`（用户唯一不变标识）精准聚合每位观众的点赞数，驱动一个带冠亚季军领奖台、纪录轮换框、徽章冠名的实时榜单；数据全量持久化（SQLite + 头像本地缓存），WebUI 控制台管理，捕获窗口（Chrome）与榜单窗口（独立浏览器窗口/OBS 源）分离，适配主播直播场景。

**零风控暴露原则**：本工具只收不发——从不向 WS 发送任何帧、不调用任何 webcast 业务接口、不需要登录态（点赞流匿名可收）。风险等级 = 开一个普通浏览器页面看直播。

## 1. 架构总览

```
┌────────────────────────────────────────────┐
│ capture/（独立子进程，patchright 驱动 Chrome） │ ← 独立窗口，可拖到副屏
│  Chrome(有头) → live.douyin.com/<房间>        │
│  page.on('websocket') → framereceived        │
│  → decodePushFrame → LikeMessage 解包         │
│  → 200ms 批量压缩上报                         │
└──────────────┬─────────────────────────────┘
               │ WS /agent（127.0.0.1:17730）
┌──────────────▼─────────────────────────────┐
│ core/（Fastify 5 + TS，单进程）               │
│  ├ 聚合引擎：secUid→计数/60s滑窗速度/峰值       │
│  ├ 校准引擎：msgId 去重 + total 差值完整度      │
│  ├ 轮次引擎：定时/手动结算 → 冠亚季军/纪录       │
│  ├ 持久层：better-sqlite3 + 头像磁盘缓存        │
│  ├ 进程监护：capture 崩溃自动重启              │
│  └ WS hub /ws：榜单快照 1s 推送 + 控制指令      │
└──┬───────────────────────┬──────────────────┘
   ▼                       ▼
WebUI 控制台            榜单展示页 /board
(localhost:17730)      (Chrome --app 独立窗口 / OBS 浏览器源)
```

**进程模型**：core 是常驻主进程；capture 是 core 派生的子进程（崩溃自愈），跑一个有头 Chrome 窗口；榜单/控制台都是 core 托管的静态页，任意浏览器打开。三窗完全解耦：关榜单不影响捕获，关控制台不影响任何东西，Chrome 窗口被误关 → core 10s 内自动重开。

## 3. 数据源（调研已确认 + 评审代理全量复核勘误）

`WebcastLikeMessage`（参考项目 955 条实测样本，评审代理用夹具全量复核）：

| 字段 | 语义 | 用途 |
|---|---|---|
| f1.f2 msgId | 消息唯一 ID（**int64**，如 7684259996728830498） | **去重**（LRU 50000；必须 64 位无损解析，见 §4.0） |
| f2 count | 本条携带的点赞数（连击≈10/条，实测范围 1–42） | **累加到用户** |
| f3 total | 房间累计点赞总数（单调递增） | **完整度校准**：Δtotal vs Σcount（仅展示 coverage，不作断言基准） |
| f5.f1 id | **仅隐私打码用户为 111111**（实测 173/955），其余为真实 uid | 不可作主键（打码用户撞号） |
| f5.f3 nickName | 昵称（约 18% 被打码"好\*\*\*"；**打码名可被多人共用**，实测"用\*\*\*"对应 2 个 secUid） | 展示 + 历史记录 |
| f5.f73 secUid | 用户唯一标识（100% 存在且唯一） | **聚合主键**（昵称会换，此键不变） |
| f5.f9.f1[i] | 头像 URL，**直接的 repeated string 字段**（非社区 proto 的嵌套 Image.url_list；部分为 small_DefAvatar.png 占位） | 头像缓存 |

### 3.1 int64 解析红线（评审 P0-1，实测确认）

参考项目 proto.ts 的 `readVarint` 用 `v |= (b & 0x7f) << shift`——JS 位运算是 32 位的，**任何 >32 位的 varint 都会被折叠损坏**（评审实测 5 个真实 msgId 全部解析错误）。参考项目不受影响（它只取 method 字符串与 f8 bytes），但本项目的 msgId 去重**绝不可照抄**。对策：

- 本项目 proto 层自带 `readVarintBig`（BigInt 实现）与 `readVarintBytes`（保留原始字节）；
- msgId 去重键 = **原始字节 hex**（零精度损失、免 BigInt 哈希开销）；
- M1 回放验收断言：随机抽取 msgId 原始 varint 字节重编码后与解析值双向一致（64 位无损）。

### 3.2 回放夹具已知基准（评审实测，M1 断言口径）

frames6.jsonl：955 条点赞中 Σcount=5551，Δtotal=6951（**嗅探夹具自身完整度 79.9%**——录制时嗅探器丢帧）。因此：

- **管线断言基准 = 喂入帧的 Σcount（5551）**：管线内不允许任何丢失/重复；
- Δtotal 仅用于 coverage 展示计算，79.9% 是该夹具的正常期望值，不是管线 bug。

辅助流：`WebcastMemberMessage`（进场，含 User → 补全用户档案）、`WebcastChatMessage`（弹幕文本，可做"弹幕互动数"扩展列）。两者复用同一 User 解析器。

## 4. 计数准确性设计（连点器场景核心）

0. **int64 无损**：见 §3.1——msgId 用原始字节 hex 做键，uid/total 用 BigInt 读出后转字符串/Number（total < 2^53 安全）。
1. **逐条累加**：每条 LikeMessage 的 count 累加到对应用户，无采样、无抽样，连点器高速连点时 count 值变大但语义不变（实测连击样本 count=10/条、total 同步 +10）。
2. **msgId 去重**：LRU Set（容量 50000，约覆盖 1000msg/s 下 50s），防 WS 重连重放。
3. **完整度校准**：房间 total 差值 vs 本端 Σcount 差值 → `coverage`（如 99.7%）。<100% 说明有帧丢失（页面卡顿/断连），控制台醒目展示，榜单不虚补（诚实原则）。断言基准见 §3.2。
4. **断连恢复**：WS 断开→capture 检测→页面自动刷新重连；期间 total 跳变缺口记入 coverage 统计。
5. **IPC 批量 + 档案分离**（评审 P1-1）：capture 侧维护用户档案表（secUid→{nick,avatar,版本号}），**档案变化才上报一次**；点赞批量条只带 `{i:msgIdHex, c:count, u:secUid}`，200ms 一批，避免每条重复携带 200B+ 字符串。

## 5. 轮次与结算（冠军体系）

- **Session（场）**：capture 成功进入一个房间 → 开场；换房/下播/停止 → 终场结算。
- **Round（轮）**：场内每 N 分钟（默认 30，可配 10/15/30/60）自动结算，或控制台"立即结算"。结算时按**本轮**点赞数排名：
  - **并列规则（评审 P2 补定义）**：likes 相同者并列同一名次（competition ranking：并列第 1 则无第 2，下一名次为第 3）；并列第 1 → 双方 champion_count 均 +1；并列第 2/3 同理。领奖台并列时同奖台高度并排显示（最多并列 3 人，超出只取先达者）。
  - 第 1 名 champion_count+1，第 2 名 runner_count+1，第 3 名 third_count+1（全量历史累计）
  - 更新全局纪录：单轮最高纪录（值+人+日期）、最长连霸（连续轮冠军）
  - 轮结果落库（round_users 全量存入，含 rank）
- **轮内 checkpoint（评审 P1-2）**：内存聚合计数每 30s 增量 upsert 到 SQLite（WAL 模式）——core 崩溃最多丢 30s 数据；重启后从 checkpoint 恢复当前轮。
- **core 守护**：启动 bat 检测 core 异常退出后自动重启（最多 5 次/10min）；UI 显示"数据已从 checkpoint 恢复"提示。
- **排行依据**：榜单默认按"本轮"排名（轮次重置有竞技感），控制台可切换"本场"（session 累计）。冠亚季军实时计算自当前排序依据。
- **换房/下播检测状态机（评审 P1-3）**：capture 每 2s 检查 page.url()：
  - 房间 URL 变更 → 上报 `room-left` → core 终场结算 → 新场开始；
  - 被重定向到 `/jingxuan`（精选页，参考项目实测的下播特征）→ 上报 `offline` → core 终场结算 + 控制台提示"已下播"；
  - 重定向到 `/verify|captcha` → 上报 `risk` → 控制台警示（被动监听预期不会触发，留检测兜底）。

## 6. 徽章体系（头像上方冠名）

按用户全量历史统计，优先级从高到低取第一个命中：

| 徽章 | 条件 | 文案 |
|---|---|---|
| 冠王 | champion_count ≥ 1 | `N冠王`（1冠王/3冠王…） |
| 点赞王 | 全库 total_likes 第 1 | `累计点赞王` |
| 亚军之最 | runner_count 全库第 1 且 ≥2 | `亚军×N` |
| 季军之最 | third_count 全库第 1 且 ≥2 | `季军×N` |
| 常客 | 参与场次 ≥ 5 | `老友·N场` |
| 新星 | 本次首秀且进过前 10 | `本场新星` |

（全库第 1 类徽章全局唯一持有者；持有者变更时旧持有者降级到次优先级徽章）

## 7. 纪录轮换框（方形，榜单标头之上）

每 6s 轮换一项（淡入淡出+数字滚动，点击可立即切下一条），候选池 = 纪录快照 + 实时动态（评审 D-1）：

1. 👑 登顶之王 — 全库冠军次数最多（值=次数）
2. 🔥 本场之最 — 本场点赞总量最多（值=赞数）
3. ⚡ 手速之王 — 本场 60s 峰值速度最快（值=赞/分）
4. 🏦 累计之最 — 全库累计点赞最多（值=总数）
5. 🏅 单轮纪录 — 历史单轮最高（值+保持者+日期）
6. 🔗 连霸纪录 — 连续夺冠最长（值=连霸轮数）
7. 🥈 亚军专业户 — 亚军次数最多（值=次数）
8. 🥉 季军常客 — 季军次数最多（值=次数）
9. 🌧 点赞雨 — 本场房间峰值速率（值=赞/分，全房合计）
10. 👥 舰队规模 — 本场参与点赞人数（值=人）
11. ⏱ 决战倒计时（动态）— 距本轮结算 mm:ss + 当前轮王
12. 💨 全房实时速率（动态）— 当前 赞/分 + 迷你条形图

里程碑插播（评审 D-3）：房间总赞突破 1万/10万/100万 时，轮换框立即插播一条"🎉 里程碑"并高亮 3s，随后回到原序列。

## 8. 持久化设计（防膨胀）

SQLite 表（只存聚合，**不存原始事件流**）：

- `users`：secUid PK、当前昵称、头像 URL、first_seen、last_seen、total_likes、champion/runner/third_count、best_speed、sessions_seen、rounds_seen、last_badge
- `nicknames`：(secUid, nickname) 唯一、first_at、last_at、hit_count —— 昵称变更全历史
- `sessions`：id、web_rid、主播名、started/ended_at、总赞、人数
- `rounds`：id、session_id、idx、started/ended_at、settle_type(auto/manual/session_end)
- `round_users`：round_id、secUid、likes、rank（该轮 ≥1 赞的所有人）
- `kv`：全局纪录（单轮纪录/连霸纪录等 JSON）

膨胀控制：round_users 每轮 ≤ 数千行（活跃房间上限量级），文本行 <100B；**头像按 secUid 归档**（`avatars/<secUid>.jpg`，URL 归一化去 query 后比对，变化才重新下载；下载失败用"渐变圆+昵称首字"占位，DefAvatar 用户同样走占位更雅观——评审实测 104 个 secUid 中 67 个有多个 CDN 域名变体 URL，按 URL sha1 去重会存重复文件）；无原始帧落盘（可选 capped debug 模式除外，默认关）。估算 8h/天 × 30 天 ≈ 数 MB 级。

徽章计算时机（评审 P2）："全库第 1"类徽章在**每次结算时**重算并落库（users.badge 冗余字段），快照推送只读字段——避免每秒全库排序。

## 9. API / WS 设计

**鉴权（评审 P2）**：core 启动时生成随机 token 写 `data/runtime-token`（捕获子进程经 env 传入；/agent 握手必须携带）。/ws 与 /api 仅监听 127.0.0.1，无需浏览器端 token（同机信任边界）。

- WS `/agent?token=`（capture↔core，内部）：上行 `{t:'hello',ver,token}` / `{t:'profiles',list:[{u,nick,av,ver}]}`（档案增量） / `{t:'likes',batch:[{i:msgIdHex,c:count,u:secUid}]}` / `{t:'room',webRid,total,online,anchor}` / `{t:'status',state,reason}`（含 room-left/offline/risk 事件）；下行 `{t:'watch',url}` / `{t:'reload'}` / `{t:'shutdown'}`
- WS `/ws`（UI/榜单）：下行 `board`（1s 快照：top50+轮次信息+纪录池+徽章）、`toast`（结算播报/登基播报/里程碑）；上行 `hello{role:'board'|'console'}`
- REST `/api/*`：`status`、`watch`(POST url)、`settle`(POST)、`config`(GET/PATCH 热更新)、`users`(分页搜索)、`user/:secUid`(详情含昵称历史)、`rounds`(历史)、`export`(JSON)、`session/reset`、`shutdown`

## 10. 前端设计

### 控制台（/）
- **概览**：捕获状态卡（Chrome 活着/完整度/房间号/主播名/在线人数）、房间切换、轮次计时器+立即结算、本场总赞、速率迷你图（SVG 自绘）、榜单内嵌预览
- **用户库**：搜索/排序（累计赞/冠次数/速度）、详情抽屉（昵称历史时间线、各场各轮数据、徽章）
- **轮次历史**：每轮前三甲+数值曲线
- **设置**：轮时长、排行依据、榜单主题（极光暗/曜石/透明OBS）、显示条数、速度窗口、开机自启说明；数据导出

### 榜单（/board）
- 顶部方形轮换框（§7，含动态项与里程碑插播）→ 冠亚季军领奖台（大头像+皇冠+徽章+实时数字滚动+奖台高度动画；并列名次并排显示）→ 4~N 名列表（FLIP 位次交换动画、300ms 内合并绘制防闪烁、速度火花⚡、连击中脉冲）
- **限额状态可视化（评审 C 项，呼应限额文档 §3.3）**：计数在 ~2800–3000 区间停滞且房间 total 增速来自他人的用户，显示"⚖️ 已封顶"小标+数字停止滚动动画——把限额机制转化为节目效果
- 极光玻璃拟态暗色主题；OBS 模式 body 透明（含竖屏 1080×1920 布局预设，适配手机直播场景）；数字 count-up 缓动插值（rAF）；1s 快照 + 前端插值=视觉上丝滑实时
- **结算仪式分级（评审 D-2）**：新王登基/连霸破纪录 → 全屏彩带粒子（canvas 一次性）；普通轮结算 → 轻量 toast 条
- 头像占位：渐变圆 + 昵称首字（覆盖下载失败与 DefAvatar 用户）

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| Chrome 有头窗口被用户误关 | core 监护 10s 重启；文档说明窗口作用 |
| 抖音改协议 | proto 层无 schema 裸解析只依赖 f8/f1/f2 结构，历史上极稳定；method 名白名单可配置 |
